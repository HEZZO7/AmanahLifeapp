## قائمة مراجعة الإعدادات — نجمعها لاحقًا خطوة واحدة في كل مرة

1. **اختيار المتجر والوضع:** نؤكد اسم المتجر والوضع المعروض قبل أي فحص. عرض بيانات Live للقراءة لا يجيز تعديلها أو تنفيذ شراء عليها.
2. **بيئة Supabase للاختبار:** من قائمة المشاريع فقط، نؤكد وجود مشروع اختبار مستقل عن الإنتاج وتطبيق اختبار يمكنه استخدامه. نطلب نعم/لا فقط؛ لا service role key أو connection string. إن لم توجد بيئة اختبار مجهزة نتوقف؛ إنشاء المشروع/تهيئته ونشر أي endpoint يتطلب موافقة منفصلة.
3. **كتالوج الاختبار:** من Products نعرض منتج اشتراك التطبيق، دون Save أو Publish. نسجّل الاسم ونوع Subscription والعملات والأسعار وفترتي month/year والتجربة الأصلية إن وجدت. نفصل ذلك عن المنتجات الرقمية المستقلة. قد يكون المستويان ضمن منتج واحد أو منتجين؛ لا نفترض هيكل الكتالوج.
4. **خريطة العروض الأربعة:** Balanced monthly/yearly وFamily monthly/yearly، مع store/product/variant IDs الصحيحة لكل بيئة. معرّفات الكتالوج ليست أسرارًا؛ لا نطلب روابط checkout الموقّعة. المنتجات التجريبية لا تصبح Live تلقائيًا، ولا نفترض تطابق IDs بين البيئتين.
5. **الأسعار الحديثة:** نطابق Price object الحالي: `category=subscription` و`variant_id` وفاصل التجديد وكميته والتجربة. الكود الحالي يتحقق من حقول recurrence القديمة على Variant؛ يلزم تأكيد وجودها أو إعداد إصلاح لاستخدام Price. لا نغيّر سعرًا.
6. **مفاتيح البيئة:** يؤكد المالك محليًا وجود مفتاح API أُنشئ في الوضع المناسب، دون نسخ قيمته أو عرضه في المحادثة. المفتاح التجريبي يستخدم بيانات الاختبار فقط وفق توثيق المزود. وجود اسم سر في Supabase وحده لا يثبت صحة قيمته؛ تثبتها لاحقًا قراءة API مصادقة من بيئة الاختبار، لا من الدردشة.
7. **Webhooks:** من Settings → Webhooks نقرأ callback والوضع والأحداث وحالة آخر تسليم. نؤكد محليًا استخدام سر مختلف للاختبار والإنتاج دون كشفه، ولا ننشئ/نعدّل endpoint الآن.
8. **وجهة الاختبار:** `https://<test-project>.supabase.co/functions/v1/app_11941c8fec_lemonsqueezy_webhook_test`. وجهة Live تحمل الاسم نفسه دون `_test` وتستخدم مشروع الإنتاج. يجب ألا يتصل اختبار بمشروع الإنتاج، أو يُرسل webhook تجريبي إلى وجهة Live.
9. **Supabase:** فحص read-only لوجود migrations الأربع بالترتيب، وتعريفات RPC والمنح وRLS وكون جدول `payment_environment` مثبتًا على وضع المشروع. migration الجديدة تتركه فارغًا عمدًا؛ لا نطلب INSERT لتفعيله في هذه المرحلة.
10. **بوابة Edge:** تحقق read-only أن webhook يسمح بالوصول دون JWT gateway، ويُلزم HMAC داخليًا. checkout يتحقق من المستخدم عبر `getUser` وبريده المؤكد. لا نستنتج هذه الإعدادات من وجود ملفات المصدر.
11. **التطبيق التجريبي:** نطابق `VITE_AMANAHLIFE_PAYMENT_MODE=test` وSupabase URL/المفتاح العام الخاصين بالاختبار وAPP_ORIGIN، ووجهات Google/email verification. لا نطلب قيمًا سرية، ولا ننشر build.
12. **الإدارة والاسترداد:** نقرأ إعدادات Customer Portal وnative trials والخصومات وdunning قبل اتخاذ قرار. لا Copy to Live أو تغيير تسعير/باقات/دفع خلال جمع الأدلة.

أسماء متغيرات الخادم المطلوبة موجودة في [trusted-lemon-payments.md](trusted-lemon-payments.md). لا نضيف مفاتيح أو أسرار webhook إلى Git أو المحادثة. نفحص قيم الإنتاج محليًا فقط دون استخدامها لإجراء دفع.

الأحداث التي يعالجها المرجع الحالي: `subscription_created`, `subscription_updated`, `subscription_cancelled`, `subscription_resumed`, `subscription_expired`, `subscription_paused`, `subscription_unpaused`, `subscription_payment_success`, `subscription_payment_failed`, `subscription_payment_recovered`, `subscription_payment_refunded`, `order_created`, `order_refunded`.

صفحة محاكاة الأحداث تذكر أيضًا `subscription_plan_changed`، لكنه غير معالج حاليًا، وصفحة event-types لا تسرده. هذا اختلاف توثيق يحتاج التقاط سلوك sandbox؛ لا ندّعي اكتمال تغيير الباقات أو نضيف اسمًا دون تحقق.

## الفترات المدفوعة: ما تثبته البيانات فعلًا

`invoice.created_at` يثبت إنشاء الفاتورة؛ `subscription.created_at` يثبت إنشاء الاشتراك. لا يثبت أي منهما بداية الخدمة المدفوعة، خصوصًا مع تجربة أو فاتورة pending تُدفع لاحقًا. و`updated_at` ليس وقت دفع موثوقًا؛ قد يتغير لأسباب أخرى.

كائن Subscription Invoice الموثق لا يقدّم `service_period_start/end` أو `billing_period_start/end`. لذلك لا نضيف شهرًا/سنة حسابيًا، ولا نستبدل تاريخ إنشاء الكائن ببداية خدمة مفترضة.

للاستحقاق الحالي: نحتاج ربط checkout موثوقًا، ومطابقة البيئة والمتجر والحساب والاشتراك والعرض، وفاتورة/طلب أولي موثوق الدفع وغير مسترد. `renews_at` في الاشتراك active يصف نهاية الدورة الحالية، لكنه في past_due يصف المحاولة القادمة؛ لا يجوز استخدام الأخير لتمديد الوصول. `ends_at` يحدد انتهاء الاشتراك cancelled/expired؛ لا يثبت وحده أن الفترة دُفعت.

المرجع الحالي ما زال ينسخ تاريخ إنشاء الفاتورة أو الاشتراك إلى `paid_access_from` ثم `current_period_start`. هذه **نافذة وصول مستنتجة وليست بداية فترة خدمة مثبتة**، ويجب عدم اعتمادها بهذا المعنى للإطلاق. نقترح الاحتفاظ بتاريخ إنشاء الفاتورة كحقل مصدر، وتسجيل وقت تأكيد الدفع الذي رآه الخادم بعنوان واضح، وترك بداية الخدمة مجهولة ما لم يقدم المزود دليلًا صريحًا. أي تغيير للحقول/المخطط يُحضّر بعد المراجعة؛ لم يُنفذ هنا.

يجب التقاط snapshot متسق مع إثبات الدفع عند كل دورة، وحفظ مصدر نهاية الوصول. لا يجوز إسناد نهاية الدورة الحالية تلقائيًا إلى فاتورة قديمة متأخرة أو إلى فترة تاريخية مفقودة. إن لم تكفِ API الحالية، نراجع فاتورة الاختبار/تأكيد دعم المزود للحدود الفعلية؛ يبقى الحقل مجهولًا والحالة بحاجة مراجعة بدل اختراع تاريخ. لا نرسل روابط PDF الموقعة أو بيانات عميل إلى الدردشة.

التكرار والترتيب لا يُعالجان بمقارنة اسم الحدث فقط: المرجع يعيد قراءة الحالة الحالية ويستخدم revision CAS وسجل الفترات وإلغاء الاسترداد الثابت. سياسة الاسترداد المعتمدة باقية: جزئي للمراجعة دون تغيير/تمديد فترته؛ كامل يلغي الفترة الخاصة به فقط مع إبقاء فترة مستقلة سارية ومثبتة الدفع.

## خطة sandbox الكاملة — مُعدّة وغير منفذة

شرط البدء: تأكيد بيئة اختبار مستقلة تعمل بالكود المطابق، وكتالوج/مفاتيح/webhook تجريبية مثبتة، وإذن منفصل لأي تهيئة أو نشر أو معاملات sandbox. لا ننشر الآن. نستخدم حسابات اختبار وبطاقات المزود التجريبية فقط، ولا نبدأ من رابط المتجر المستقل لإثبات اشتراك التطبيق.

لكل حالة نسجل: التوقع، UTC للملاحظة، أسماء/IDs تجريبية مُرمّزة، حالة المزود قبل/بعد، نتيجة تسليم webhook، revision وعدد سجلات الحدث والفترات، والوصول من حساب مالك وعضو وحساب غريب. النتائج: غير منفذ/نجح/فشل/محجوب. لا نخزن بريدًا أو nonce أو توقيعًا أو مفتاحًا أو signed URL أو سجلات عملاء حقيقية.

1. **الهوية والعودة:** افتح الاشتراك في التطبيق التجريبي دون دخول، ثم اختبر Google وفي حالة مستقلة email verification. النجاح: العودة للاشتراك، ورفض checkout قبل التحقق، وعدم الدفع أو منح باقة بمجرد التسجيل. يتطلب حساب المالك/حسابات اختبار؛ الآلي يغطي return path فقط.
2. **العروض:** افتح كل عرض من التطبيق بعد الدخول. قارن السعر والفاصل والعملة والمنتج، وتأكد أن جلسة الخادم لا تُتاح لمتغير آخر أو لحساب آخر. ألغِ الخروج قبل الشراء إن كان المقصود مجرد فحص عرض. اختبارات العبث بالجسم تُشغّل آليًا في العزل.
3. **دفع أول ناجح:** بعد إذن sandbox، نفذ شراء تجريبي من checkout الخادم. تحقق من سجل الدفع المزود وربطه بالحساب نفسه، ثم webhook موثّق ونافذة وصول بمصدر واضح. العودة أو الإيصال وحدهما ليسا دليل التفعيل؛ الحساب الغريب لا يحصل على البيانات.
4. **فشل الدفع الأول:** حالة مستقلة ببطاقة فشل تجريبية من دليل المزود. لا تُنشأ فترة مدفوعة ولا رسالة تفعيل ناجح. لا نخلط نجاح إنشاء checkout مع نجاح دفعه.
5. **التجربة إلى الدفع:** حساب بتجربة تطبيق سارية، ثم شراء Balanced وFamily بحالتين منفصلتين. تبقى التجربة مرة واحدة ويُحترم تدرج الميزات؛ انتهاء التجربة يعيد الحساب إلى الاستحقاق المدفوع المثبت فقط. حساب استنفد التجربة يجب أن يرسل الخادم له `skip_trial=true`.
6. **التجربة الأصلية للمزود:** نسجل native trial إن كانت موجودة. on_trial أو فاتورة صفرية ليست دليل دفع؛ لا نفترض أن تجربة التطبيق تبدأ/تتزامن معها. إذا كان العميل يحصل على trial بالمزود دون وصول متوافق بالتطبيق فهذه فجوة تحويل تستلزم قرارًا قبل الإطلاق.
7. **تجديد حقيقي داخل sandbox:** يلزم حدوث تجديد فعلي وإصدار فاتورة renewal مدفوعة جديدة، ثم التقاط نهاية الدورة الجديدة والتحقق من تمديد واحد فقط. Simulate event ليس بديلًا عن تغير الحالة لدى المزود. لا نزعم وجود ساعة اختبار قابلة للقفز.
8. **تعثر وتجدد الدفع:** بعد دورة مدفوعة، نجرب فشل renewal ثم نجاح recovery داخل sandbox عند توفر أدوات المزود. لا يمدد past_due/unpaid الوصول إلى موعد إعادة المحاولة؛ فاتورة مدفوعة مستقلة فقط تسمح بالاستعادة. لا نعتبر failed initial payment اختبارًا كافيًا لفشل renewal.
9. **إلغاء التجديد:** نلغي تجريبيًا من Customer Portal بعد الدفع. يجب بقاء الوصول الكامل حتى النهاية المثبتة مع حد ends_at، دون فقد البيانات. إعادة التفعيل قبل ends_at حالة منفصلة؛ لا تخلق فترة دفع جديدة تلقائيًا.
10. **الانتهاء:** ننتظر/نستخدم آلية موثقة ومصرحًا بها لإنهاء الاشتراك التجريبي فعلًا، ثم نفحص قراءة/تصدير/مغادرة الأعضاء ومنع الإضافة/التعديل/الحذف/الانضمام. إرسال اسم expired وحده بينما API ما زالت active لا يثبت انتقال الحالة.
11. **استرداد كامل للحالي:** ننفذه على الفاتورة/الطلب التجريبي المعني بعد الإذن، ثم نتحقق من revocation للفترة. إن وجدت فترة مستقلة سارية ومثبتة الدفع، يبقى استحقاقها؛ لا نحذف البيانات.
12. **استرداد قديم:** بعد إثبات renewal أحدث، نسترد فاتورة سابقة ونفحص بقاء الفترة الأحدث، ثم نعيد إرسال الحدث القديم ونكرر النتيجة. لا نغيّر user binding يدويًا لتجهيز الحالة.
13. **استرداد جزئي:** نتحقق من تغير حالة الفاتورة التجريبية، ورفع review flag دون تعديل أو تمديد فترتها؛ renewal مستقل مدفوع لاحق لا تمنعه مراجعة فاتورة قديمة.
14. **التكرار:** من سجل webhook التجريبي أعد إرسال تسليم سبق نجاحه. نتوقع عدم تكرار الفترة/الربط/التمديد. التوازي يُختبر آليًا أيضًا بجلسات PostgreSQL مستقلة.
15. **التأخير وترتيب الأحداث:** بعد تحديث حقيقي أحدث، أعد إرسال تسليم محفوظ أقدم من السجل. لا يتراجع الاستحقاق إلى الحالة القديمة ولا يُمحى الاسترداد. إعادة تسمية حدث جديد ليست اختبار تأخير لحمولة قديمة؛ الآلي يغطي أيضًا snapshots متزامنة/قديمة.
16. **انقطاع webhook والاسترداد منه:** نعطّل المعالجة في بيئة مختبر مصرح بها فقط، نتحقق من فشل/محاولات التسليم ثم الاستعادة. إعادة تسليم حدث فاشل غير مطبق يجب أن تعمل؛ التعافي بعد نفاد محاولات المزود أو فقد الحدث يتطلب عامل reconciliation المقترح أدناه. لا نحذف journal لتجاوز deduplication.
17. **إعادة الاشتراك وتغيير الباقة:** نفحص الإلغاء ثم العودة قبل النهاية، والشراء بعد انتهاء الربط، والترقية والتخفيض وتغيير monthly/yearly منفصلة. حاليًا الربط القائم يمنع checkout جديدًا حتى بعد expiry؛ وتغيير variant يبقي العرض القديم ويُرفع للمراجعة، ولا يمدد الفترة. هذه حالات محجوبة وظيفيًا وليست نجاحًا تجاريًا؛ تحتاج تصميمًا وإصلاحًا منفصلًا.
18. **المنتجات الرقمية والفصل بين البيئتين:** شراء sandbox مستقل لا يمنح تطبيقًا مدفوعًا. حدث test على معالج live والعكس يُرفض في اختبار معزول، دون إرسال أي شيء إلى الإنتاج. تنزيل الملفات الرقمية معطل في Test mode وفق المزود، فلا ندعي اختبار التسليم الفعلي منه.

### قيد مدة اختبار التجديد

يوصي دليل المزود بمنتج تجريبي يومي والانتظار لأول تجديد في اليوم التالي، ثم محاكاة أحداث subscription_payment_* من تلك البيانات. لكن checkout الحالي يقبل month/year فقط ويرفض daily. لذلك لا يمكن تنفيذ توصية daily كتجربة تطبيق كاملة دون إعداد مختبر محدود ومراجعة إضافية. البدائل: انتظار تجديد شهري حقيقي لباقة الاختبار المطابقة، أو الموافقة لاحقًا على harness/عرض يومي معزول لا يتسلل إلى Live. تغيير billing_anchor يولد حالات proration؛ لا نقدمه على أنه renewal مطابق.

## التجارب، إعادة الاشتراك، الباقات وPaddle — نتائج الكود

- تجربة التطبيق تبدأ بـRPC مشتق من auth.uid ووقت الخادم، مرة واحدة؛ لا تعتمد على localStorage. وجود مستخدم بلا trial_used يجعل checkout يسمح بتجربة Lemon Squeezy الأصلية إن كان العرض يوفرها، بينما حالة on_trial لا تنشئ استحقاق دفع. يلزم مطابقة التجربتين قبل الإطلاق.
- `payment_create_intent` يمنع أي حساب له subscription_id مرتبط، حتى expired. Customer Portal يسمح بإدارة الربط القائم؛ لا يوجد مسار مكتمل لشراء اشتراك بديل بعد انتهاء القديم. تحديث API الحالي لا يجيز افتراض resume بعد انتهاء ends_at.
- تغيير العرض ليس ترقية مدفوعة مكتملة. proration/zero invoice/paid pause غير محسومة؛ لا نغيّر سياسات المزود أو نمنح عرضًا من metadata.
- يوجد `app/frontend/supabase/functions/app_11941c8fec_paddle_checkout/index.ts`: يستدعي API الحية لـPaddle من المصدر، ويشتق السعر من إعدادات عامة دون فصل sandbox/live مماثل.
- يوجد `app/frontend/supabase/functions/app_11941c8fec_paddle_webhook/index.ts`: يتحقق من HMAC لكنه لا يتحقق من عمر timestamp، ويقبل user/tier/billing من custom_data ويكتب مباشرة في جدول الاشتراكات دون سجل فترات Lemon أو CAS/منع التكرار. يمكنه العبث بإسقاط الاشتراك المشترك إن كان منشورًا ومهيأً؛ لا نزعم أنه منشور أو قابل للاستغلال فعليًا دون فحص الإعدادات. لا نمسحه أو نعطله الآن.
- فحص ملفات src الـ164 لم يجد استدعاء checkout Paddle، لكن `src/pages/PricingPage.tsx` يعرض نص قبول الدفع عبر Paddle؛ وSubscriptionContext وSubscription يحتفظان بنوع/تعليقات Paddle. عدم وجود زر ليس إثباتًا لتعطيل endpoints أو زوال deployments قديمة. يحتاج ذلك قائمة Edge Functions وwebhooks وإعدادات الأسماء فقط دون أسرار.

## الاسترداد التقني من webhook مفقود — أقل حل موثوق مقترح

الموجود الآن: معالجة متزامنة مع canonical reads، ومراجعات وتكرار، وعودة 503 عند الأخطاء. المزود يوثق حتى ثلاث إعادات إضافية بعد الفشل، بتأخير تصاعدي مثل 5/25/125 ثانية؛ ليست طابورًا دائمًا. توجد إعادة تسليم يدوية من Settings → Webhooks. لا يوجد worker مجدول، أو inbox دائم يكفي لإصلاح كل حدث غير مربوط، أو تنبيه مؤكد على أخطاء المعالجة.

نقترح استخدام Supabase القائم فقط: inbox/jobs صغيرة محمية داخل PostgreSQL، وعامل Edge واحد يستدعيه Cron كل 15 دقيقة مبدئيًا. المعالج يتحقق من HMAC والبيئة أولًا، ويحفظ أدنى سياق موثق لازم لإعادة المحاولة، مثل event key وprovider IDs وintent hash؛ لا يخزن nonce أو بيانات بطاقة. لا يرد 200 إلا بعد حفظ عمل قابل للاسترجاع أو تطبيقه. العامل يعيد قراءة المزود ويستخدم نفس منطق الإسقاط وCAS وسجل الفترات، ويعيد المحاولة مع backoff/حد أقصى ومراجعة يدوية وتنبيه بعد الإخفاق. المتابعة الدورية تشمل الحسابات المرتبطة، لا حسابات يختارها عميل.

يلزم **مسار reconciliation خدمي مستقل** ومفتاح عملية مشتق من البيئة والاشتراك ونسخة الحالة الموثقة؛ إعادة إرسال حدث قديم تم تطبيق digest الخاص به ستنتج duplicate ولن تصلح بالضرورة فاتورة أحدث مفقودة، حتى لو أعاد المعالج قراءة المزود. لا نصنع webhook أو توقيعًا مزيفًا للعامل، ولا نحذف journal لتخطي الحماية.

الربط الأول المفقود يعاد من سياق intent الموثق المحفوظ أو تسليم المزود الأصلي؛ لا نربط بالإيميل أو custom user_id. لا يستطيع reconciliation اختراع حدود فترات تاريخية لم تُحفظ؛ يبقي الغامض للمراجعة. لا نحتاج مزود queue أو اشتراك جديد؛ توافق Cron/الحصص والتكلفة الفعلية يحتاج فحص المشروع. لم يُنشأ job أو جدول أو endpoint في هذه الجولة.

## ما يمكن تنفيذه آليًا وما يحتاج المالك

- **آلي ومعزول:** اختبارات الهوية/tampering، HMAC المزور، mode mismatch، التكرار والتزامن وترتيب الأحداث، حساب الاستحقاق والاسترداد وربط الحساب، RLS/RPC، lint/build/Deno. الدليل الحالي CI عند 81948e0؛ ليس دليل production.
- **يحتاج دخول المالك، قراءة فقط:** الوضع والكتالوج والـPrice والتجارب والبوابة وdunning ووجهات webhook وتسليماته ووجود مشاريع Supabase والمخطط والمنح وأسماء الإعدادات والإصدارات المنشورة.
- **يحتاج إذنًا منفصلًا وبيئة اختبار جاهزة:** إنشاء/تغيير أي مورد sandbox، تشغيل معاملات تجريبية، نشر endpoint حتى لو تجريبيًا، اختبار Google/email، إلغاء/استرداد تجريبي، إعادة تسليم أحداث وتشغيل تمرين انقطاع. لن ينفذ شيء من ذلك قبل بوابة الإذن.
- **ممنوع الآن:** نشر أو دمج أو migrations/كتابة إنتاج، نسخ منتجات إلى Live، تغيير live webhooks/المفاتيح/التسعير، أو دفع/استرداد حقيقي.
