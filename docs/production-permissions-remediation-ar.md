# خطة معالجة صلاحيات الإنتاج — مسودة للمراجعة

**القرار: No-Go للاشتراكات المدفوعة؛ لا تنفيذ إنتاجي أو دمج أو نشر.** المنتجات الرقمية وLemon Squeezy مستقلان، ولا تغييرات على المتجر أو الدفع أو Cron أو الأسرار.

## حدود الدليل

المالك أبلغ عن CSV من 111 صفًا، وأكد الصلاحيات الواسعة وسياسة الاشتراكات وEXECUTE العائلة وغياب معظم كائنات الدفع والسياسات العامة للإشعارات. **ملف CSV نفسه غير مرفق في هذه الرسالة ولم يُقرأ صفًا بصف**. التصنيف أدناه يعتمد على ملخص المالك ومراجعة المصدر الفعلية؛ لا نزعم فحص ملف غير متاح أو تنفيذ استغلال إنتاجي. يلزم إرفاق CSV metadata الآمن قبل اعتماد مطابقة أسماء السياسات والأعمدة والأنواع والمالكين والوراثة.

المراجع المقروءة: الويب/Edge في PR #2 عند `7bcf54a75377115ef48670a8b63f8095e5f02e84`، والمحمول/PR #1 عند `a2c004893714d0e68655afd8084edad215714e8c`. هذه نسخ مصدر، وليست إثباتًا لنسخ الإنتاج المنشورة.

## ما أُعدّ فعليًا

1. **Migration 007**: مستقل عن جداول الدفع؛ يمكن اختباره كإصلاح إشعارات منفصل. يعيد تطبيق ACL/RLS بصورة idempotent، دون UPDATE/DELETE/نسخ بيانات أو تغيير Schema للأعمدة أو مفاتيح/فواتير. يرفض علاقات غير عادية وTriggers غير مراجعة وصلاحيات دور API مميز، ثم يتحقق من عدم بقاء وصول موروث زائد؛ أي فشل يعيد المعاملة كاملة.
2. تفضيلات authenticated: SELECT/INSERT للأعلام الستة وخمسة حقول موقع مع user_id للقراءة/الإدراج فقط؛ UPDATE للأعلام/الموقع فقط؛ لا DELETE أو TRUNCATE أو تعديل markers/updated_at/هوية. كل صف مقيد بـauth.uid().
3. Push: لا وصول جدول لـPUBLIC/anon/authenticated؛ service_role فقط للعمليات الأربع الضرورية، دون TRUNCATE/TRIGGER/REFERENCES أو تفويض منح.
4. إصلاح النسخ الاحتياطي المرافق وقائمة أعمدة موحدة واختبارات تنقية. الأخطاء المعادة من التخزين تُفحص ولا تُعرض استعادة ناجحة رغم رفض قاعدة البيانات. الاستعادة العامة ليست عملية متعددة الجداول ذرية؛ أي فشل قد يأتي بعد استعادة بيانات محلية/جدول آخر، ويجب أن يظهر فشلًا وإمكانية إعادة المحاولة.
5. **اقتراح defaults منفصل**: global + public للـtables/functions/sequences التي ينشئها postgres؛ يغلق PUBLIC EXECUTE المدمج للدوال حتى لو لم توجد ACL صريحة. لا يغير ACLs للكائنات الحالية، ولا يعالج تلقائيًا منشئي كائنات آخرين. يحتاج موافقة نطاق منفصلة قبل التطبيق.
6. **001–006 ليست قابلة لإعادة التشغيل عشوائيًا**؛ تظل Migrations مرتبة ومسجلة مرة واحدة مع preflight خاص بها. لا نغيّر تاريخها لادعاء أن جميعها idempotent. 002 قابل للتكرار ضمن شروطه، و007 والاقتراح المنفصل الجديدان يخضعان لاختبار تكرار فعلي.

## الاختبارات المعزولة المطلوبة في CI

- النموذج السابق يعيد قراءة وتعديل anon لصفوف الإشعارات وTRUNCATE، ثم يعود بالمعاملة؛ لا يتصل بإنتاج أو خدمة Push.
- 007 يُشغّل مرتين، مع تحقق أن الصفوف كاملة، والأعلام false، وتسجيلات الأجهزة وmarkers لم تتغير؛ تبقى قيود/فهرسة الجدول كما هي.
- anon مرفوض؛ authenticated بلا هوية يرى صفر صف ولا يُدرج؛ حساب A لا يقرأ/يعدل B ولا يغير user_id أو حقول الخادم، ولا يقرأ مفاتيح Push.
- upsert الموقع والاستعادة المنقحة والإدراج الأول المصرح تنجح؛ الخادم يقرأ ويحدّث markers ويسجل/يحذف جهازًا ويحذف بيانات حساب تجريبي.
- منح عبر دور موروث غير معروف تؤدي إلى **فشل كامل وrollback**، ثم ينجح التشغيل بعد تنظيف fixture فقط.
- defaults المقترحة تُختبر مرتين في CI فقط؛ ACLs الحالية تبقى، وإنشاء table/function/sequence وهمية لا يمنح العميل وصولًا تلقائيًا. لا استدعاء فعلي لتلك الدالة ولا provider.
- اختبارات الاشتراكات/التجارب/المدفوعات والعائلة السابقة تبقى لإثبات منع raw writes، وعدم إعادة تجربة، واستحقاق مدفوع مع إثبات، ورفض anon RPC. سبعة اختبارات إضافية لنسخ التفضيلات المنقحة.

نتائج CI الفعلية وروابطها تُسجل في وصف PR عند اكتمالها؛ الاختبارات ليست دليلًا أن 007 أو 001–006 مطبقة إنتاجيًا أو أن PostgREST الفعلي يتصرف تمامًا مثل SQL fixture. أنواع أعمدة الموقع في fixture نموذج مطابق لاستخدام المصدر، وليست ادعاء قراءة schema الإنتاج؛ لا تطبيق قبل CSV كامل.

## ترتيب الطرح المقترح — يحتاج موافقة جديدة

1. استلام CSV كامل والتحقق من المخططات/الأنواع/المالكين/السياسات/العضوية وTriggers، ونسخ Edge المنشورة. جمع snapshot ACL/policy آمن وخطة استعادة قبل أي تعديل. لا إعادة فحص Cron أو قراءة أسراره.
2. تجهيز بيئة مستضافة معزولة معتمدة واختبار JWT حقيقي لحسابين، دون معاملات دفع حقيقية أو تغيير وضع المتجر الحالي. لا موارد جديدة دون موافقة.
3. **مسار الإشعارات المستقل**: طرح عميل الويب المتوافق للنسخ الاحتياطي، والتحقق من اعتماد العملاء؛ إبقاء عميل المحمول المتوافق للتفضيلات. بعدها نشر endpoint المشدد الموجود أصلًا في PR وفق بوابة التوافق السابقة، ثم 007 فقط بعد موافقة منفصلة. اختبر مصدر الويب والمحمول المعتمدين؛ لا تنشر جميع تغييرات PR #2 دفعة واحدة لمجرد إصلاح الإشعارات.
4. proposal defaults منفصل بعد اعتماد تأثيره على كل منشئي كائنات المشروع؛ ليس تابعًا تلقائيًا لـ007.
5. **مسار الاشتراكات مستقل**: أصلح المحمول والتجارب أولًا، احسم توافق الأجهزة القديمة ووعد مدة التجربة، جهّز النسخ الاحتياطية والتطابق والتكامل الحقيقي، ثم حضّر 001–006 بالترتيب مع الدوال/الخوادم/العملاء المطابقة. لا تمنح raw legacy rows صفة دفع ولا تحذف حساباتها. لا تفتح الدفع أثناء هذا التحضير.
6. لا إطلاق مدفوع قبل إثبات إعداد catalog/test-live وربط الحساب والفاتورة والفترة والاسترداد والإلغاء والتجديد والاستعادة/المصالحة والمراقبة، وقرار Go منفصل. المنتجات الرقمية لا تُربط بهذا القرار.

## قائمة تحقق إنتاجية بعد موافقة منفصلة

هذه **قائمة قبول مستقبلية وليست إذنًا بالتنفيذ الآن**:

- [ ] أُغلق نقص CSV وحددت PostgreSQL/schema والنسخ المنشورة الفعلية؛ أخذت نسخة إعدادات/بيانات آمنة وخطة استعادة مجرّبة.
- [ ] طرح العميل المتوافق مثبت؛ لا توجد نسخة BackupRestore قديمة نشطة تتطلب DELETE أو INSERT داخلي؛ الأجهزة القديمة لا تكتب تجربة إلى الاشتراكات.
- [ ] metadata بعد التطبيق: لا PUBLIC/anon أو منح أعمدة متبقية؛ لا TRUNCATE/TRIGGER/REFERENCES/WITH GRANT OPTION للمستخدم؛ لا وراثة دور مميز أو BYPASSRLS.
- [ ] سياسات الإشعارات تستهدف الأدوار الصريحة وتفرض uid، ولا سياسة permissive عامة تلغيها؛ Push server-only.
- [ ] اختبارات REST بحسابين: القراءة والكتابة الذاتية للأعمدة المحددة تعمل، الأجنبية والهوية والحقول الداخلية مرفوضة؛ JWT غائب/فاسد مرفوض. لا تعتمد على SQL Editor صاحب الامتياز.
- [ ] location upsert الفعلي واستعادة نسخة قديمة وإعادة المحاولة بعد 401/403/5xx لا تمس markers أو Push ولا تعرض نجاحًا كاذبًا. لا تغيّر بيانات عميل حقيقي للاختبار.
- [ ] subscribe/unsubscribe وget/update والحذف المفوض والجدولة تحفظ العمليات المطلوبة. لا إشعار حقيقي ضمن هذا التدقيق؛ اختبار التسليم يحتاج موافقة منفصلة.
- [ ] 001–006 وRPCs الفعلية تطابق النسخ المعتمدة؛ start_trial لا يأخذ user_id/توقيت العميل؛ فحص الاستحقاق لا يقبل raw tier/past_due أو legacy row كدليل.
- [ ] anon لا ينفذ مساعدات العائلة؛ authenticated لا ينفذ primitives الدفع؛ search_path ومالك كل دالة مطابقان؛ defaults المستقبلية مقيدة وفق النطاق المعتمد.
- [ ] لا يُختبر TRUNCATE أو حذف بيانات على الإنتاج؛ كفاية إثبات سحب المنح في metadata والاختبارات المدمرة في العزل فقط.
- [ ] recovery/reconciliation/backup والبروتوكول التجاري للدفع مثبتة في عزل حقيقي. التحسن في ACL وحده لا يغلق No-Go.

## التراجع والتشغيل

- أي preflight/اختبار نهاية في 007 يفشل: ROLLBACK للمعاملة كاملة؛ لا تكمل بعمليات يدوية ولا تتجاوز الحارس. ثبت ذلك بحالة وصول موروث في CI.
- 007 لا يمس صفًا؛ لا تحتاج استعادة بيانات روتينية أو حذفها. قد يأخذ تغيير السياسات/الأقفال وقتًا؛ قِس الأقفال في العزل وجدول التنفيذ المستقبلي دون تعديل مهمة Cron الحالية.
- إذا فشل عميل بعد تطبيق مستقبلي: أوقف طرح العميل/الكود الجديد واعمل forward fix متوافقًا. حافظ على RLS الذاتية، ومنع anon/TRUNCATE، وPush server-only. لا تعُد إلى PUBLIC true أو خدمة تقبل استبدال user_id.
- لا ترجع إلى BackupRestore القديم الذي يعيد أسرار الأجهزة/حقول الخادم. أي منح مؤقت محدد للأعمدة/الصف الذاتي يحتاج مراجعة وموافقة منفصلة، ولا يوصف بأنه rollback آمن تلقائيًا.
- لا إسقاط لجداول أدلة الدفع أو ledger أو إعادة تشغيل تجارب أو إعادة اعتماد raw legacy paid status في rollback. حفظ البيانات والمراقبة أولًا، واستعادة انتقائية فقط إذا ثبت تلف وبموافقة جديدة.
- proposal defaults لا يغير الكائنات الموجودة؛ لا تُعد المنح الواسعة للرجوع. أضف فقط منحًا صريحة لكائن مستقبلي معتمد إن احتاج التطبيق إليه، بعد مراجعة.

**الجاهزية:** يمكن مراجعة إصلاح الإشعارات واختباراته في المسودة؛ تطبيق الإنتاج متوقف على CSV الكامل والتوافق المستضاف والموافقة. حماية الاشتراكات ليست جاهزة للإطلاق بسبب فجوة النشر والمحمول والتكامل الفعلي. التكلفة الإضافية لاختبارات CI لا تتطلب خدمة مدفوعة جديدة ضمن الحدود الحالية؛ تكلفة عزل مستضاف أو بناء/توزيع المحمول لاحقًا غير مثبتة ولم تُنشأ موارد لهما.
