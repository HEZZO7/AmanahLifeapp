# توافق كتابة الموقع واستعادة تفضيلات الإشعارات

هذا إصلاح عميل محدود بعد `0aa8f340811fa55b95da87ba24adb27024e3b3e0` في PR #2 المسودة. لا تعديل لـ007 أو RLS/GRANT أو الفوترة أو Edge/Cron أو الإنتاج. إطلاق اشتراكات التطبيق يبقى **No-Go**، والمنتجات الرقمية مستقلة.

## السلوك النهائي

`PrayerTimes.syncLocationToSupabase` و`BackupRestore.handleImport` يستخدمان singleton `notificationPreferenceStorage`، وهو facade قابل للاختبار من `notificationPreferenceWrite.ts`:

1. فحص أن جلسة SDK الحالية موجودة وتخص الحساب المتوقع. هذا فحص اتساق في العميل، لا إثبات تشفير؛ PostgREST يتحقق JWT وتفرض 007/RLS الهوية والصلاحيات.
2. `UPDATE` جزئي للأعمدة المسموحة مع `.eq('user_id', account)` و`count: 'exact'`، بلا `.select()` أو `return=representation`. لا يحتوي جسم PATCH على user_id أو id أو markers أو timestamps. العدد 1 يؤكد الكتابة، والعدد المفقود/غير المتوقع يفشل.
3. إذا كان العدد صفرًا، plain INSERT للحقول المطلوبة مع user_id الحساب نفسه؛ دون merge-duplicates أو ON CONFLICT UPDATE. الحقول غير المطلوبة تأخذ defaults عند الإدراج فقط.
4. إذا سبق جهاز أو إجراء خادمي آخر لإنشاء الصف الفريد، فإن 23505 يؤدي إلى PATCH إضافي واحد فقط. لا يكتب حقولًا افتراضية فوق تفضيلات الصف الفائز، ولا يغيّر هوية الصف. سائر الأخطاء تفشل دون fallback أوسع.
5. يعاد فحص الجلسة قبل/بعد الطلبات. التبديل للحساب الآخر يمنع المحاولات اللاحقة وتأكيد النجاح. طابور لكل حساب داخل singleton يحافظ على ترتيب طلبي الموقع والاستعادة في هذا العميل؛ ليس قفلًا موزعًا بين الأجهزة.

الموقع يكتب حقوله الخمسة فقط؛ auto يمسح manual city دون تغيير الأعلام. الحساب المحلي للصلاة يبقى متاحًا عند فشل المزامنة، مع رسالة واضحة أن المزامنة لم تنجح ويمكن إعادة المحاولة من إعدادات الموقع. الاستعادة تزيل هوية النسخة القديمة وحقولها الداخلية وتحتفظ بالأعلام/الموقع الصالحين؛ لا تعلن نجاح الاستيراد إذا رفضت كتابة التفضيلات. الاستعادة العامة لعدة جداول/localStorage ليست معاملة ذرية؛ سلوك الجداول الأخرى لم يتغير.

## الاختبارات

- 23 اختبارًا معزولًا للواجهتين: تحديث موجود/إدراج جديد، قيم false، هوية نسخة أجنبية، رفض Auth/شبكة/تخزين، count مفقود، التعارض الفريد ومحاولة إعادة محدودة، تبديل الحساب، وترتيب الفشل وإعادة المحاولة. لا شبكة أو خدمات مدفوعة.
- CI الكامل يشمل lint/build وفحص TypeScript محدود لربط facade بـSupabase client الفعلي، إضافة إلى المجموعة السابقة دون تغيير منطق الاشتراكات.
- Job PostgreSQL/PostgREST الحالي على PG15 وPG17 يستخدم **Supabase SDK الحقيقي 2.106.0** لاستدعاء facade نفسه المستخدم في الشاشتين. الجلسات محلية ثابتة في الاختبار، وJWT والتوقيع وSET ROLE/RLS تُفحص فعليًا عبر PostgREST. لا محاكاة للاستجابة SQL أو لعدد الصفوف في اختبارات HTTP.
- حسابان A/B: مزامنة خمسة حقول دون reset للأعلام، استعادة أعلام متغيرة مع هوية/حقول داخلية في النسخة تُهمل، وعدم تغيير الحساب الآخر. فحص الطلبات يمنع قراءة أعمدة محجوبة أو كتابة الهوية أو طلب representation/merge-duplicates.
- حساب C **موجود أصلًا في auth fixture المحلي دون صف تفضيلات**: جهازان وهميان بJWT نفسه يجعلان PATCHين يريان صفر صف، ثم INSERTان حقيقيان أحدهما 201 والآخر 409/23505؛ المحاولة الإضافية تحفظ الموقع وأعلام الاستعادة معًا. SQL بعد الاختبار يتحقق من القيم وmarkers/defaults، ويحذف صف C التجريبي فقط، ثم يتحقق من بقاء الحسابين الأصليين وتسجيلات Push دون تغيير.
- اختبارات التوافق الحالية إلزامية: أي رفض للحفظ عبر facade يُفشل CI. طلب merge-duplicates القديم يبقى اختبار رفض متعمدًا، وليس تدفق العميل الحالي. لا يُمنح SELECT(id) أو UPDATE(user_id) لإخفاء خلل التوافق.

## ما بقي مستضافًا

لم يُنشأ مشروع أو حساب Supabase مستضاف، ولم تُنفذ طلبات إنتاجية. النجاح المحلي لا يثبت إعداد Supabase gateway أو JWKS أو إصدار PostgREST المستضاف أو تعابير defaults الحقيقية المحجوبة في CSV أو النسخ المنشورة للويب/المحمول/Edge.

مشغّل `notification-postgrest-integration.mjs` القائم يشمل الآن facade وSDK نفسه. بعد موافقة منفصلة واختيار **مشروع معزول قائم معتمد**، استخدم إعداد الحسابين وملف المتغيرات خارج Git من [وثيقة 007](notification-007-validation-ar.md)، دون production ref أو service key أو إرسال JWT في الدردشة. يلزم Node22+ وتثبيت dependencies الموجودة أصلًا؛ من `app/frontend`:

```sh
node --env-file=/absolute/path/outside-repo/notification-isolated.env --experimental-strip-types --loader ./tests/preference-test-loader.mjs tests/notification-postgrest-integration.mjs
```

في الوضع المستضاف تُفحص جلستا الحسابين عبر `/auth/v1/user` قبل أي كتابة، ثم تُستعاد الحقول المسموحة المؤكدة السابقة. لا يُنشأ C ولا تُنفذ SQL أو عمليات حسابات في هذا الوضع؛ اختبار السباق والإدراج الأول محلي CI فقط. تظل الحاجة لاختبار أول إدراج/التزامن في الاستضافة وخطة تنظيف معتمدة قبل ادعاء التكامل الكامل. عند انقطاع قسري/فشل cleanup يلزم مشغل العزل، ولا تُستخدم حسابات عملاء حقيقيين.

التقرير يميز securityPassed وclientCompatibilityPassed وhostedAuthVerified؛ rolloutReady يبقى false لأن النتيجة ليست إذن نشر.

## ترتيب الطرح المقترح — ليس إذن تنفيذ

اعتماد اختبارات المصدر وHTTP → نجاح Supabase المستضاف المعزول مع defaults وcount=exact وJWT الحقيقي → إثبات نسخ العملاء واعتمادهم، مع عميل المحمول المتوافق للتفضيلات → طرح عميل ويب بهذا الإصلاح أولًا → التحقق من نسخة get/update_preferences المشددة المنشورة وفق بوابة التوافق السابقة → موافقة منفصلة وsnapshot/preflight ثم **007 وحده** → تحقق ومراقبة منقحان. لا نشر PR كله أو 001–006 ضمن إصلاح الإشعارات.

عند التراجع احتفظ بكتابة PATCH/INSERT الآمنة؛ لا تعد إلى upsert القديم أو منح واسعة أو endpoint القابل لاستبدال الهوية. مشاكل ما بعد التطبيق تحتاج forward fix معتمدًا. فحوص MAINTAIN والتراجع في007 تبقى دون تغيير. لا تكلفة API أو خدمة مدفوعة جديدة؛ CI يخضع لحدود GitHub Actions.
