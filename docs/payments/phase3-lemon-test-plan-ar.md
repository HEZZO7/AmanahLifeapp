## دليل القبول

لكل حالة: source/package/workflow SHA، اسم الحالة، PASS/FAIL/BLOCKED، عدد
deliveries/الكتابات، انتقال الحالة وأكواد آمنة. لا بريد/UUID/Customer ID/JWT أو
signature أو secret أو URLs خاصة أو bodies/logs خام. تُسمى الحسابات A وB فقط.
أي خطوة ناقصة تبقى NOT TESTED؛ لا retry عشوائي أو mock Auth لإكمال القبول.

| الحالة | الإجراء اللاحق المصرح به | النتيجة المطلوبة |
|---|---|---|
| إغلاق افتراضي | A موثق يطلب Checkout قبل الموافقة | رفض503 قبل إنشاء intent/طلب مزوّد؛ B لا صلاحية |
| intent A | بعد تفويض Test مستقل وتأكيد المالك، A يختار balanced_monthly من landing→Subscription→Login | جلسة المستخدم هي مصدر الهوية؛ intent واحد دائم قبل POST، nonce مخزن كـhash، لا user_id موثوق من المتصفح |
| دفع اختبار | استخدام وسيلة اختبار Lemon الرسمية على Checkout المؤكد Test | store/product/variant/mode صحيحة، skip_trial=true، مبلغ/عملة/ضريبة معتمدة؛ success=true لا يفعّل وصولًا |
| توقيع وملكية | تسليم Webhook الحقيقي إلى endpoint Test | توقيع صحيح على raw bytes، canonical subscription/invoice/order، trusted binding لـA وCustomer مملوك له، ثم proof مدفوع محدود المدة |
| B وهجوم الربط | B يحاول تعديل custom_data/offer أو استعمال معرّفات A، أو فتح portal له | لا إسناد للحساب B ولا كشف تاريخ A؛ لا دليل دفع من email/metadata وحدها؛ Customer مشترك يتوقف للمراجعة |
| تكرار/تأخير | إعادة التسليم من لوحة Test، ثم إعادة حدث أقدم بعد انتقال أحدث | أثر proof واحد، لا تمديد proof نفسه ولا استعادة بعد refund ولا رجوع إلى الحالة القديمة؛ ledger/inbox موثقان |
| إلغاء | إلغاء التجديد في portal Test | provider cancelled، وصول A حتى paid-through المثبت فقط، وإدارة الفواتير تبقى متاحة؛ انتهاء الوصول عند الحد |
| renewal | توليد تجديد Test بالطريقة التي يتيحها المزوّد فعليًا | فاتورة renewal مدفوعة مستقلة وربط صحيح؛ لا created_at+مدة مفترضة أو منح من renews_at وحده |

| full refund | استرداد كامل لحالة Test المرتبطة | proof المقابل مسحوب بثبات؛ إعادة success القديم لا تعيده؛ renewal مستقلة لا تُمحى باسترداد قديم |
| partial refund | استرداد جزئي في Test | review_required، لا تمديد غير مثبت، سياسة الحق القائم معتمدة من المالك؛ لا افتراض full refund من boolean وحده |
| paused/resumed/expired | الحالات التي يدعمها Test فعلًا | حالة مرجعية صحيحة، لا حق من status فقط، والاستئناف لا يخلق دفعة أو يعيد مدة مستردة |
| reconciliation | worker موثوق ومصرح به يستدعي recoverDeliveries/reconcileBindings مرة محددة | ربط/دليل مرجعي من API Test، dedup وrevision، إصلاح حدث مفقود، ولا endpoint مصالحة مجهول عام أو cron غير مراجع |
| التزامن/النتيجة الغامضة | طلبان متزامنان ثم محاكاة فقد رد POST في مشروع Test المملوك | حجز واحد؛ لا POST ثانٍ تلقائي حتى بعد TTL؛ لا تحرير حجز إلا بعد تأكيد المزوّد بعدم وجود التزام |

تُكرر حالات الكتالوج للخطط الأربع بعد نجاح الحالة الأولى A/B. لا تُخترع قدرة
تسريع تجديد/expiry أو رقم بطاقة أو endpoint Test مختلف؛ إن لم يدعم المزوّد
الحالة في Test تُسجل BLOCKED ويحدد المالك بديلًا رسميًا قابلًا للمراجعة.

## موانع الاستنتاج

لا يغطي native إرسال Webhook عبر hosted Edge gateway أو Deno المنشور أو
سلوك المزوّد. لا تُنشر notification writer/BackupRestore غير المتوافقة ضمن هذا
القبول. يلزم patch مستقل للعائقين الموثقين في مراجعة المصدر قبل إطلاق المنتج.
سياسات الاسترداد والتجديد والرسوم والاحتفاظ واعتماد الأسعار تبقى مسؤولية مالك
المنتج؛ الخطة لا تُقرّها ولا تغيّرها.
