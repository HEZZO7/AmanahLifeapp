- المستودع المؤكد عبر موصل GitHub هو `HEZZO7/AmanahLifeapp`، ومعرّفه `1272912875`.
- لم تظهر إعدادات Git تخص proxy أو URL rewrites. متغيرات `HTTP_PROXY` و`HTTPS_PROXY` ونسختاهما بالحروف الصغيرة تشير إلى الوكيل المطلوب `proxy:8080`؛ `ALL_PROXY` غير مضبوط. فُحص `NO_PROXY` دون نشر قيمه؛ GitHub ليس ضمن استثناءاته. لم تُطبع بيانات اعتماد أو عناوين وكيل حساسة.

## ما نُفّذ فعليًا

### ملكية push_notify

- كاتب `update_preferences` يقبل فقط ستة مفاتيح إشعار معروفة بقيم boolean. تُرفض الحقول المحمية والمجهولة، والمصفوفات والقيم غير الصحيحة، قبل الكتابة. `user_id` مشتق من المستخدم المصادق عليه ويُثبت بعد الحقول المسموحة؛ لا يمكن استبداله من JSON.
- جرى تشديد صيغة Bearer، وحصر ناتج `get_preferences` في الأعلام العامة، وإزالة أخطاء SDK الخام وعناوين الأجهزة من السجلات المعدّلة، وإضافة `Cache-Control: no-store`.
- إعادة تسجيل جهاز لا تعيد تفعيل تفضيلات معطّلة: إنشاء defaults يستخدم `ignoreDuplicates`، وتُفحص نتيجة التهيئة. إلغاء التسجيل يبقى مقيدًا بمالك JWT، ويُفحص خطأ الحذف.
- إرسال المستخدم يبقى لنفسه فقط، وإرسال scheduler لحساب آخر يتطلب السر الداخلي المكوّن. أسماء الأنواع المختصرة الموجودة عند callers تُحوّل إلى عمود مسموح؛ فشل قراءة التفضيلات يمنع الإرسال بدل تجاهل اختيار المستخدم.

### BackupRestore وmigration 007

- التصدير والاستعادة يستخدمان allowlist ثابتة للجداول والحقول القابلة للنقل: أعلام الإشعارات وموقع الصلاة ولغتها وتوقيتها، وإعدادات الملخص البريدي، وحقول سجل البحث. لا `SELECT *` للتصدير، وتُقرأ الصفوف بصفحات مرتبة ومقيدة بالمستخدم.
- لا تُقرأ أو تُكتب push registrations أو مفاتيحها أو جدول الاشتراكات. تُتجاوز أقسامها القديمة مع تنبيه، ولا تُستعاد الهوية أو timestamps الداخلية أو scheduler markers. الجدول غير المعروف يُرفض قبل أول تعديل.
- استعادة صف التفضيلات تستخدم `UPDATE` للحقول المسموحة فقط، و`INSERT` بملكية الجلسة عند غيابه، مع إعادة محاولة واحدة إذا سبق كاتب آخر إلى الإنشاء. لا DELETE لصف التفضيلات ولا upsert يطلب `UPDATE(user_id)` المحظور في 007. لم تتوسع grants أو RLS.
- تُفحص كل نتيجة DB؛ لا نجاح أو reload بعد فشل. يُتحقق من كامل الملف قبل أول كتابة، وتأتي كتابة localStorage بعد العمليات البعيدة الناجحة. تبقى سلسلة HTTP/localStorage غير ذرية، ويشرح التأكيد ورسالة الفشل احتمال تطبيق بعض التغييرات قبل الخطأ، خصوصًا استبدال سجل البحث.
- مفاتيح localStorage محصورة في بيانات شخصية معروفة وأسماء الصلاة والذكر؛ لا sweep عام لكل `amanah-*`، ولا إعادة لعب auth أو entitlement caches أو بيانات `excused_*` الحساسة. حد ملف الاستيراد 10 MiB، وحد الصفوف المدعومة 10,000 لكل جدول.

### حذف الحساب والاحتفاظ بالسجلات

- صفحة الحذف وSettings والتأكيد يشرحون بالعربية والإنجليزية أن سجل الفوترة أو حجز الدفع يمنع الحذف التلقائي حتى مراجعة الدعم، بما في ذلك بعد إلغاء التجديد أو انتهاء الاشتراك. طلب الحذف لا يلغي الاشتراك.
- أُضيف مسار واضح لإدارة الاشتراك والتواصل مع الدعم. أُزيل وعد الحذف اليدوي خلال 30 يومًا ووعود محو جميع البيانات؛ وُضح النطاق المدعوم واستقلال النسخ الاحتياطية والأجهزة الأخرى.
- رد رفض الفوترة يوضح أن الإلغاء أو الانتهاء لا يمحوان التاريخ أو يضمنان الحذف. بقيت حواجز DB ومسار Auth الذري وسلوك عدم تسجيل الخروج عند الرفض كما هي.

## حدود النتيجة وبوابات الإطلاق

Phase 4A نُفّذ على المصدر الصحيح، وهذه نتيجة اختبارات مصدر وواجهات محلية. لا توجد نتيجة SQL/WASM جديدة، أو Native PostgreSQL/GoTrue/Deno integration، أو اختبار توصيل Web Push حقيقي. doubles واختبارات عرض React لا تثبت ACL/RLS على مشروع مستضاف أو rollback فعليًا أو تزامن اتصالات مستقلة.

إصلاح توافق 007 هنا يخص BackupRestore؛ كاتب الموقع المباشر في `PrayerTimes.tsx` ما زال يستخدم legacy upsert ويحتاج مراجعة منفصلة مع ACL الحقيقي قبل اعتماد جميع عملاء الإشعارات. يلزم أيضًا جرد schema وtriggers والعملاء والإنتاج وخطة retention، وإعادة اختبارات SQL وNative على المصدر النهائي عند تفويض ذلك. نجاح سابق لا يُنسب إلى هذا الفرع.

لم يتغير `main`، ولم يحدث نشر، أو migration مستضافة، أو تفعيل فوترة، أو dispatch لـGitHub Actions. workflows الموجودة يدوية فقط ولم تتغير. نشر فرع المصدر لا يجيز أيًا من هذه الإجراءات. **الإنتاج والفوترة يظلان NO-GO.**
