# Notification preferences authorization — PR #2

Scope: only `update_preferences` and `get_preferences` in `app_11941c8fec_push_notify`. No AI, billing, digest, reconciliation, Cron, Web Push sender or production change. This is prepared code for review, not a deployment.

## Call path and corrected boundary

`NotificationSettings` -> `useNotifications.updatePreferences` -> POST `app_11941c8fec_push_notify` with the session bearer token and six boolean toggles. `useNotifications` also reads them using `get_preferences`. Server-side dispatch now intercepts both actions before constructing the legacy service-role client and returns their response directly, including authorization/validation/storage failures. The previous unvalidated-spread update block and wildcard read block are removed.

Supabase Auth verifies the JWT using the project's existing public key. No decoded-but-unverified claims or client identity are accepted. No JWT or internal push secret alone bypasses Auth verification; the scheduler secret is not an authorization method for preferences. Missing/invalid auth returns 401; Auth/storage/configuration failures return a sanitized 503. Top-level target/control fields are rejected even if they match the caller's own identity.

The explicit write allowlist is `prayer_reminders`, `bill_reminders`, `habit_reminders`, `fasting_reminders`, `savings_reminders`, `general_activity`; values must be literal booleans, including false. Empty/invalid patches and unknown keys are rejected atomically with 400 before privileged storage is constructed. User IDs, role/privilege fields, creation/update timestamps, sent markers and location metadata cannot be supplied here. The store independently validates the patch again, fixes the table and user_id conflict target, and places the verified identity and server updated_at after the validated flags. No request-selected SQL/filter/table/header reaches the database client.

Reads select only the six toggles plus user_id, filter by verified identity, check the returned owner and expose only the toggles. Missing rows/null flags use the same true defaults as the current web client. A foreign/corrupt result or any database error fails closed. Client/scheduler internal fields are not returned. Responses are no-store, and these two new paths do not log database errors, tokens or preference contents.

## Service role and database scope

Auth verification no longer needs service_role. For these two actions, the admin key is obtained only after successful Auth and full validation, and is confined in the new fixed-table/fixed-user storage capability. Existing subscribe/unsubscribe/send branches retain their original database model and code. No new environment secret is introduced; existing SUPABASE_URL/SUPABASE_ANON_KEY/SUPABASE_SERVICE_ROLE_KEY availability needs verification before any future approved hosted validation.

**Why service_role is retained for preference storage:** the existing endpoint uses privileged access and the actual notification-table grants/RLS/constraints have not been supplied. Silently switching to user-level storage or inventing new policies could break legitimate reminders/settings. This preparation narrows request-level authorization without expanding any database privilege, but does not make the credential itself least-privilege across the entire existing function. Replacing it with an audited RLS-scoped client or narrow RPC is a later decision after table evidence; no privilege changes are proposed blindly.

No migration is required for this endpoint patch. It still relies on the existing six boolean columns, user_id uniqueness/onConflict behavior and updated_at already used by the old endpoint. Production column types/defaults/constraints and direct-table RLS remain unverified. `PrayerTimes.syncLocationToSupabase` separately upserts timezone/language/prayer location fields using the user client; BackupRestore can also restore this table. These callers are unchanged. Protection of direct PostgREST access and internal sent markers is not proved by the endpoint fix and is a hosted-readiness blocker until grants/RLS are audited. Use `notification-preferences-readonly.sql` for metadata only after the owner chooses to collect it; it is not executed by CI or this task.

## Preservation and tests

The existing six-boolean web payload still works, including all-false updates. Partial upserts omit location/internal fields. Scheduler, reminder timestamps, VAPID keys and the send_notification authorization/sending logic are not changed. The pre-existing subscribe default-upsert behavior is also unchanged; this patch does not redesign notification delivery or resubscription. Other/native clients that relied on arbitrary fields in preferences must be checked before deployment; unknown fields now receive 400 intentionally.

`tests/notification-preferences.test.mjs` executes the actual preference action and scoped store against a deliberately privileged two-user fake backend under fetch/HTTP/TCP denial. It covers nested/top-level identity and internal-field injection, invalid/prototype-shaped inputs, six-flag compatibility, partial updates, own-only reads, foreign/corrupt rows, missing/forged auth, internal-secret rejection, Auth/credential/database errors, redaction and delegation of unrelated actions. It never calls Web Push or real Supabase. Deno checks the production push_notify entry point. The existing CI pipeline remains in place; no AI source was re-audited or changed for this task.

These tests do not exercise real JWT validation, hosted gateway settings, PostgREST upsert semantics, production RLS or device delivery. Table-policy/constraint metadata and an approved isolated hosted verification are still required before deployment. CI results and the security self-review are recorded in the PR report. No production queries, notification sends, resource creation, secret changes, merge or deployment occur here; paid subscriptions remain No-Go and independent digital products are unaffected.

## Security self-review and future release gate

Reviewed boundaries: both preference actions are intercepted before legacy storage, failed requests cannot fall through, no client user_id is accepted at either level, patch copying is allowlisted twice, verified identity is applied last, read filtering and ownership checks agree, and only safe fields leave the endpoint. Authentication is mandatory even with the internal push header. Subscribe/unsubscribe action blocks are compared byte-for-byte with the branch baseline. The send block has only an erased TypeScript index assertion for its existing dynamic preference lookup, required by the newly added full-entrypoint Deno check; its runtime logic is unchanged. A narrow SDK adapter avoids recursive generic-type comparison without weakening runtime validation.

Before any separately approved rollout: inspect read-only table metadata, verify real user-A/user-B JWT isolation and direct-table RLS in an approved isolated environment, confirm defaults/partial-upsert preservation and client payload compatibility, then coordinate deployment without touching push Cron or secrets. If a future rollout fails, use a compatible protected version or fail closed for these two actions; do not restore the vulnerable spread or weaken table policies. Production operations require explicit approval.
