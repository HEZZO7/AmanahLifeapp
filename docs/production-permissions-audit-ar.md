# تجهيز أدلة صلاحيات Supabase — قراءة فقط

الحالة: **No-Go للاشتراكات المدفوعة**. الملف مُجهّز للمراجعة؛ لم يُشغّل على الإنتاج، ولم تُطبّق Migration أو تتغير صلاحيات أو أسرار أو مهام. بيع المنتجات الرقمية مستقل. لا توجد فاتورة خدمة جديدة لهذه المرحلة.

## ما تم تجهيزه

- الملف: `docs/production-permissions-evidence-readonly.sql`.
- **استعلام واحد، نتيجة واحدة، وتصدير CSV واحد**؛ الأقسام المرقمة 00–07 تنظّم النتيجة، وليست استعلامات مستقلة.
- المرجع المثبت: PR #2 عند `2c133fbfda2a5af4427fafc9a26054b801ffb3b4`، وMigrations 001–006 في هذا المرجع. أي تطوير لاحق يحتاج تحديث المقارنة.
- تمت مراجعة `docs/notification-preferences-readonly.sql`. يبقى ملفًا تاريخيًا دون تعديل، والملف الجديد يغطيه لهذه المرحلة؛ **لا حاجة إلى تشغيل الملفين**. يتجنب الجديد إخراج قيم defaults ونصوص الدوال ووسائط Triggers التي كان يمكن أن تظهر في صيغ التعريف الكاملة.
- النطاق: جدول الاشتراكات والتفضيلات وثمانية جداول دفع متوقعة، وأي علاقات إضافية ذات أسماء مناسبة ضمن بادئة التطبيق، وأقسامها الموروثة/Partitions؛ RPCs التطبيق في مختلف المخططات، ودوال سياسات/Triggers الجداول المستهدفة، والأدوار الموروثة وACLs المستقبلية والواجهات Views التابعة.
- لا استعلام على صفوف التطبيق أو `auth.users`، ولا تشغيل لأي RPC، ولا قراءة قيم Vault أو أوامر Cron أو Webhook أو مفاتيح الدفع. لا تُصدّر أجسام الدوال أو قيم Defaults أو نصوص تعريف Triggers/Views. تُحجب السلاسل النصية داخل تعبيرات RLS، وتُظهر بصمات التعريف فقط عند الحاجة للمقارنة.

## طريقة الهاتف — بعد موافقة المالك على تشغيل الملف

1. افتح ملف SQL من فرع PR #2، ثم **Raw** أو قائمة الملف ونسخ المحتوى كاملًا. لا تنسخ ملف Migration.
2. افتح Supabase، وتأكد من اختيار مشروع AmanahLife المقصود. انتقل إلى **SQL Editor → New query**؛ استخدم عرض سطح المكتب في المتصفح إذا لم تظهر القائمة.
3. الصق الملف كاملًا. اترك دور لوحة SQL الافتراضي المصرح لك باستخدامه؛ لا تضف تبديل أدوار أو أوامر أخرى. يحتاج الفحص رؤية بيانات تعريف الكتالوج، وليس صلاحية مستخدم التطبيق العادي.
4. **بعد الموافقة فقط** اضغط Run مرة واحدة. التشغيل يقرأ الكتالوج؛ لا يحاول تعديل صلاحيات أو محاكاة شراء أو تفعيل اشتراك.
5. من النتائج اختر **Export / Download CSV** بحسب واجهة Supabase، وسمّه مثلًا `amanahlife-permissions-evidence-YYYY-MM-DD.csv`. تأكد أن التصدير يشمل كل الصفوف وليس الصفحة المرئية فقط. إذا بدت النتيجة مقطوعة، لا تُفسّرها على أنها فحص مكتمل.
6. راجع أسماء الأعمدة: `section`, `object`, `evidence`. يمكنك مشاركة هذا CSV؛ لا تُرفق سجل استعلامات آخر أو صور أسرار أو بيانات عملاء. إذا ظهر خطأ، شارك نص الخطأ وموضعه فقط، ولا تُعدّل الصلاحيات لحلّه بنفسك.

لا يُطلب التشغيل الآن؛ الإعداد منفصل عن الموافقة على الجمع اليدوي. إذا تعذر نسخ النص الطويل من الهاتف، يمكن إرسال الملف نفسه إلى محرر نصوص على الهاتف ثم نسخ محتواه كاملًا، دون تقسيمه أو تشغيل جزء من CTE.

الاستثناءات المهمة في **الحالة النهائية بعد 005–006**:

- `payment_require_mode` و`payment_entitlement` و`payment_apply` و`payment_create_intent`: لا EXECUTE لأدوار API الثلاثة؛ تستدعيها الدوال الموثوقة أو أُغلقت كمسارات قديمة.
- بقية RPCs `payment_*` في المرجع: service_role فقط. `current_subscription()` و`start_trial()` و`ai_entitled()`: authenticated فقط.
- `account_family_entitled(uuid)`: service_role فقط؛ لا تفترض أن أي دالة باسم entitlement متاحة للعميل.
- دوال Trigger الجديدة للحماية: لا EXECUTE عام/عميل/خادم API. لا تحتاج Trigger قائم إلى منح استدعاء RPC عام حتى يعمل.
- مساعدات العائلة القديمة المذكورة في 002 تحفظ المنح القديمة المحددة؛ الحارس الخادمي/سياسات العائلة يحددان الاستعمال الفعلي. مولّد join code في 003 هو SECURITY INVOKER وفق المصدر؛ لا تصنّف كل دوال المشروع على أنها يجب أن تكون DEFINER.
- Migrations 001–006 تُغلق منح كائناتها صراحة، لكنها **لا تضيق الافتراضيات المستقبلية على مستوى المشروع**. هذه فجوة معروفة من مراجعة المصدر، وليست تأكيدًا بأن كل RPC منشور مكشوف.
- جدول التفضيلات ليس محل Migration تقوية ضمن 001–006؛ إصلاح endpoint لا يثبت سلامة الوصول المباشر عبر PostgREST.

## حدود الأدلة وحالة التحقق

- البصمات SHA-256 في قسم 04 تُقارن أجسام 30 دالة نهائية من مصدر PR حرفيًا، وليس مجرد الاسم؛ المسافات تؤثر. ثلاث مساعدات قديمة لم تُعد تعريف أجسامها في 001–006، فتظهر بصمتها المتوقعة فارغة؛ لا نخمن المطابقة.
- حتى `source_matches_pr=true` لا يثبت تطبيق Migration كامل أو صحة المالك/ACL أو القيود أو RLS أو البيانات السابقة. metadata لكل ذلك منفصلة. لا نقرأ جدول سجل Migrations أو محتوى أوامره.
- قسم 05 يميز المنح الفعالة عن إمكانية تعيين الدور، ويدعم اختلاف حقول عضوية PostgreSQL قبل/بعد الإصدار16. PUBLIC يظهر كجهة منح، وليس دورًا قابلاً لتسجيل الدخول.
- لا تُصدر تعبيرات Constraints أو Defaults أو Triggers/Views كاملة. بصماتها تحفظ إمكانية مقارنة معزولة لاحقة، لكنها لا تثبت دلالتها الآن. نص RLS محجوب السلاسل؛ إذا أخفى الحجب تفصيلًا مؤثرًا فتبقى تلك السياسة غير محسومة حتى مراجعة آمنة إضافية.
- جرد Views يستخدم تبعيات الكتالوج. SQL الديناميكي والدوال القديمة ذات أسماء أخرى والمخططات المكشوفة في إعداد API لا يمكن إثباتها بالكامل منه. لا يثبت نجاح SQL Editor بوصفه postgres أن أدوار PostgREST محمية؛ الفحص يجمع صلاحيات تلك الأدوار دون تبديل إليها، ثم نحتاج اختبارين فعليين لحسابين في بيئة معزولة معتمدة.
- **لم ينفَّذ هذا الاستعلام** على أي قاعدة؛ المراجعة الحالية قراءة المصدر وتجهيز الملف، وليست شهادة تشغيل PostgreSQL. نتيجة غير مكتملة أو خطأ لا يُفسّران كدليل أمان. إن ظهر خطأ توافق إصدار، نصلح الاستعلام وحده بعد استلام نص الخطأ؛ لا تغييرات إنتاجية.

## القرار والخطوة التالية

الأولوية الحرجة قبل النشر: إثبات أن مستخدم التطبيق لا يستطيع كتابة الاشتراك/أدلة الدفع أو استدعاء RPC تفعيل لحساب آخر، وإغلاق أي وصول عابر للحسابات على التفضيلات. الصلاحيات الواسعة وسياسة INSERT القديمة **مثبتتان تاريخيًا بأدلة المالك، وحالتهما الحالية تحتاج نتيجة هذا الجمع**. لا يوجد دليل جديد يبرر تحويل No-Go إلى Go.

الخطوة التالية الوحيدة: مراجعة ملف الاستعلام والحصول على موافقة المالك على تشغيله يدويًا وتصدير CSV. بعدها نقارن النتائج ونقترح إصلاحًا محددًا منفصلًا؛ لا إصلاح تلقائي ولا تغيير صلاحيات ضمن جمع الأدلة.
